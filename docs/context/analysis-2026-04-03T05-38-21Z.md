## Goal Of The Pass

Turn the app from a fixture-backed shell into a real hybrid pipeline while keeping the visible UI mostly stable and preserving the “show the machinery” philosophy.

## Key Hypotheses

### Hypothesis 1

If we keep the current UI shell and only replace the data/runtime layer, we can get a much more credible system demo without spending time on redesign.

Outcome: worked.

Evidence:
- The current shell handled real progressive rows and cells without needing a new navigation model.
- The internals surfaces got much stronger once the backend started producing real events and usage records.

### Hypothesis 2

If we expose execution internals loudly, the app will read as engineering-heavy rather than “agent theater.”

Outcome: mostly worked.

Evidence:
- Real provider calls, checkpoints, metrics, skipped verifications, and tool-call summaries made the execution trace much more believable.
- The remaining gap is that some actor labels and trace wording still feel a little stylized and should keep getting more concrete.

### Hypothesis 3

The cheapest live path should be enough for a first vertical slice if we keep the architecture lean.

Outcome: partially worked.

Evidence:
- Brave + Gemini was enough to get real end-to-end behavior.
- Gemini free-tier quota became the dominant limiting factor very quickly.
- The architecture survived because we added budget guards and fallback behavior.

### Hypothesis 4

Canonicalization flags alone will be enough to keep the visible result table clean.

Outcome: failed.

Evidence:
- Duplicate rows still leaked through the results API.
- The lesson is that canonicalization is not complete until the presentation/query layer respects the duplicate markers.

### Hypothesis 5

A run that cannot keep spending LLM budget should still remain useful if the system falls back to explicit, weaker states.

Outcome: worked.

Evidence:
- After the runtime changes, the app no longer crashed under provider quota pressure.
- The run stayed observable and completed with a mix of accepted and uncertain rows instead of dying mid-flight.

## Real Constraints We Hit

- Gemini free-tier request limits
- Vite hot reload interacting with an in-memory runtime
- local sandbox friction around repeated localhost smoke calls
- stale Playwright browser state
- low-quality discovery sources producing superficially plausible but potentially misleading rows

## Design Adjustments That Paid Off

- Adding extraction and verification caps
- compacting overflow rows into fallback states instead of letting the run fail
- persisting metrics and activity coarsely rather than trying to log every micro-step
- keeping rejected/unmatched candidates visible instead of hiding all non-accepted work
- separating semantic row state from processing state

## Design Adjustments Still Needed

- stronger duplicate clustering and suppression
- stronger source-tier policy for accepted rows
- clearer live-provider metadata in evidence and traces
- real Cloudflare-backed truth state instead of in-memory local state
- a better contract for rendering unsupported vs not_found in the compact table vs details

## Quality Of The Current System

Strong:
- dynamic live preview
- real search/fetch/extract/verify path
- explicit observability
- visible abstention behavior
- stable test/build pipeline

Weak:
- free-tier limits shape output quality hard
- source quality can still pull in noisy candidates
- duplicate handling is improved but not yet battle-tested enough
- local live behavior is still more fragile than a real queue-backed Cloudflare deployment will be

## Engineering Tricks Worth Remembering

- Keep browser/E2E tests fixture-backed even while live-provider integration advances.
- Budget guards are not just defensive programming; they are part of the product story on free tiers.
- If the system is meant to show its work, skipped work is worth surfacing too.
- In-memory local runtimes are fine for fast iteration, but only if we remember that hot reload can erase the very state we are trying to inspect.

## What We Would Do Differently Starting Over

- Add graceful background-run rejection handling earlier.
- Put explicit provider-budget guards in the first live-provider PR, not the second.
- Treat duplicate suppression as an API concern from the start, not just a canonicalization concern.
- Add a slightly stronger source-trust filter before row creation so weak community/discussion pages do less downstream damage.

## Strongest Story Beats For Later Communication

- “We kept the UI stable and turned the toy backend into a real one.”
- “The first live run immediately found the real bottleneck: quota, not styling.”
- “We chose graceful degradation over fake confidence.”
- “We instrumented the system so every failure taught us something visible.”
