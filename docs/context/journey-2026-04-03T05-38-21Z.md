## Session Summary

This session moved the project from a convincing fixture-backed shell into a real hybrid search system with live Brave search, live Gemini planning/extraction/verification, aggressive in-app observability, and explicit cost/budget accounting.

The visible shell stayed stable on purpose. The work was concentrated in the runtime, provider contracts, progressive data plumbing, and engineering-facing introspection.

## What We Thought Going In

- We wanted the app to feel like an engineer-facing system demo rather than a polished-but-opaque product mock.
- We expected live-provider integration to surface the first real constraints:
  - quota pressure
  - runtime stability under failure
  - duplicate canonicalization bugs
  - places where “agent theater” would feel fake unless it was grounded in real calls and real state transitions
- We wanted to stay disciplined about bloat:
  - no fake multi-agent swarm
  - no unnecessary fallback-provider zoo
  - no architecture inflation before the core loop was real

## What Happened

- The live Brave + Gemini path was wired into the Worker-style runtime.
- The preview endpoint started returning real dynamic plans instead of fixture-only plans.
- End-to-end live runs started working locally and exposed real search/fetch/extract/verify activity in the app.
- The internals surfaces became much more credible because they were now backed by real usage records, stage durations, tool-call traces, and cost metrics.
- A real free-tier failure hit during extraction: Gemini returned `429 RESOURCE_EXHAUSTED`, and the dev server crashed because the background run rejection was not being swallowed safely.
- We tightened the runtime to degrade gracefully instead:
  - cap live candidate fan-out
  - cap extraction calls
  - cap verification calls
  - compact overflow rows into heuristic fallback states
  - keep the run observable instead of crashing the app
- A real duplicate-row bug surfaced:
  - both `PostgreSQL` and `Postgres` survived into the visible results
  - canonicalization had marked the duplicate, but the API/store layer still returned it
  - we fixed the results filtering path so duplicates stop leaking into the table payload

## What Worked

- The decision to build the contract and observability model first paid off. When live providers came online, the system already had places to put:
  - stage events
  - usage ledger records
  - tool-call traces
  - reward-style runtime summaries
  - row and cell provenance
- Progressive rendering held up well:
  - rows appeared early
  - cells advanced from pending to filled/blank/weak states
  - engineers could see the pipeline doing work rather than waiting for a monolithic final answer
- The dedicated unmatched section is still the right demo move. It frames rejection as deliberate work, not noise.
- Keeping the architecture lean was the right call. Brave + Gemini + a Worker-style runtime already created enough real complexity to learn from.

## What Did Not Work

- Free-tier Gemini assumptions were too optimistic for unconstrained extraction fan-out.
- Letting background run promises reject without a guard was a bad failure mode. It made the dev loop feel fragile and fake.
- Canonicalization alone was not enough; duplicate suppression also had to happen at the result delivery layer.
- Some evidence metadata still carried fixture-era naming/history and exposed places where the live path needs a final cleanup pass.
- The local environment was occasionally noisy:
  - localhost curl access sometimes needed escalation
  - Playwright browser state could wedge on a stale shared profile
  - Vite hot reload plus in-memory runtime made some smoke runs hard to interpret unless executed carefully

## New Things We Learned

- The system can tell a much stronger story when the execution trace is backed by real provider calls. Even partial success feels far more credible.
- Free-tier constraints are not just a cost concern; they are a product-shaping force. They force:
  - retrieval budgets
  - selective verification
  - explicit abstention
  - graceful degradation strategies
- A noisy engineering demo benefits from showing skipped work, not just completed work. “Verification skipped due to budget guard” is informative and honest.
- Some low-quality discovery sources can still produce superficially plausible structured rows. That makes source policy and canonicalization more important than we might have hoped.

## Tricks And Workarounds We Used

- Swallowed background run rejections after terminal state was persisted so the dev server stayed alive.
- Added per-run extraction and verification caps so free-tier quotas did not dominate the behavior.
- Used heuristic fallback extraction for overflow or failed rows so the table stayed coherent without pretending those rows were equally trustworthy.
- Used direct local smoke runs against the Worker-style API to validate real stage/state behavior without waiting for full Cloudflare deployment.
- Forced Playwright/browser tests to stay in fixture mode so they remained deterministic while live-provider development continued separately.
