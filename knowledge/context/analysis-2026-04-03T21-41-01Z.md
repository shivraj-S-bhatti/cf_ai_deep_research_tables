## What We Thought

- More visible internals would make the system feel more credible.
- Exposing agent-like decomposition in the main UI would help judges understand the system.
- The existing runtime complexity was acceptable because the app only handled small row counts.

## What Actually Happened

- The product UI became overloaded with debug concerns.
- The app began to feel like three products at once:
  - research product
  - debug console
  - ops/eval dashboard
- The main interactive stall was not exotic algorithmic complexity. It was request fan-out and repeated detail loading.

## What Worked

- The core shell still holds up:
  - query
  - preview
  - progressive table
  - unmatched partition
  - detail pane
- Progressive row rendering remains a strong product behavior.
- Cell state modeling is still one of the better parts of the system.
- Deep observability is still useful when separated from the product view.

## What Did Not Work

- Anthropomorphic agent naming in the main UX.
- Reward proxies in the main sidebar.
- Trace-heavy hydration during normal runs.
- Fetching every row detail on every polling cycle.
- Letting candidate documents masquerade as final entities.

## Key Conclusions

- We overfit to engineer theater before stabilizing the product loop.
- The main pain is constant-factor blowup, not asymptotic class.
- Intermediate structured representations leaked too directly into the main UX.
- Candidate-document vs entity separation was under-specified.
- Full-detail polling was an avoidable architectural mistake.
