## Prior Product Polling Shape

During an active run, the client was effectively doing:

- `GET /threads/:id`
- `GET /runs/:id/results`
- `GET /runs/:id/events`
- `N x GET /runs/:id/results/:rowId`

every `700ms`, where `N` was the number of visible rows.

This created:

- `O(R)` requests per polling cycle
- repeated transfer of event payloads
- repeated transfer of row-level evidence and sources

## Runtime Complexity Notes

High-level stage complexity remains:

- planning: `O(1)`
- discovery: `O(Q + candidate_docs)`
- fetch: `O(S)`
- extraction: `O(R * C)`
- evaluation and verification: `O(R * K)`

The main practical problem was the constant factor:

- event spam
- raw payload duplication
- per-row detail fan-out
- over-eager polling

## New Product Polling Shape

The current refactor changes the main workspace to:

- `GET /threads/:id`
- `GET /runs/:id/results`

on a slower polling schedule, with:

- row detail only on selection
- debug trace only in the debug route

This makes the normal polling shape effectively constant with respect to visible row count.
